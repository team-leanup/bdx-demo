## 🔴 지금 당장 손봐야 할 5가지

### 1. 회원권으로 결제한 매출이 삭제 후에도 남아있어요

**어떤 일이 일어나나요?**
손님이 회원권 8만 원 + 현금 2만 원으로 10만 원짜리 시술을 받았어요.
사장님 입장에서 이 손님의 **누적 매출은 10만 원**으로 잡혀요. (정상)

그런데 이 기록을 삭제하면 매출에서 **2만 원만 빠지고 8만 원은 그대로 남아요.**
→ 손님 카드에 실제로는 없는 8만 원짜리 유령 매출이 계속 보이는 거예요.

**어디서 만나나요?** 시술 기록을 잘못 등록해서 지울 때마다 발생.

---

### 2. 회원권 만료일에 결제하려고 하면 거부될 수 있어요

**어떤 일이 일어나나요?**
회원권 만료일이 "6월 1일"이라면, 그날 하루 종일 결제할 수 있어야 정상이에요.
근데 **6월 1일 아침 9시 전에는 시스템이 "만료됨"으로 거부**해버려요.

원인은 서버가 한국 시간이 아닌 다른 시간대(UTC)로 만료를 계산하기 때문.

**어디서 만나나요?** 만료일 당일 오전에 시술받으러 온 손님 → 결제 거절 → 사장님 당황.

---

### 3. 다른 샵의 회원권 상품이 삭제될 수 있어요

**어떤 일이 일어나나요?**
회원권 상품을 지울 때, "이게 정말 내 샵 거 맞아?" 라는 확인을 코드에서 안 해요.
지금은 Supabase(DB)가 막아주고 있지만, 정책 한 줄만 잘못 건드리면 **다른 샵 회원권이 삭제되는 사고**가 날 수 있어요.

**어디서 만나나요?** 사고 시나리오. 평상시엔 안 보임. 시한폭탄 같은 거예요.

---

### 4. 다른 샵 고객에 메모를 쓸 수 있어요

**어떤 일이 일어나나요?**
"스몰토크 노트"(고객 메모) 기능에서, 어느 샵 거인지 표시를 안 하고 저장해요.
악의적으로 작정하면 **A 사장님이 B 사장님 고객 카드에 메모를 남길 수 있어요.**

**어디서 만나나요?** 일반 사용에선 안 일어나요. 다만 보안 사고가 터지면 책임 추적이 어려워져요.

---

### 5. 손님이 다른 예약 정보를 바꿔치기할 수 있어요

**어떤 일이 일어나나요?**
사전상담 링크에서, 손님이 URL의 예약 ID를 다른 샵 예약 ID로 바꿔서 제출하면 **그 예약 내용이 자기가 입력한 걸로 덮어 써질 가능성**이 있어요.

서버에서 "이 예약이 정말 이 샵 거 맞아?" 확인을 하는지 코드만 봐서는 알 수 없어요. 직접 확인이 필요해요.

**어디서 만나나요?** 일반 손님은 모르고, 작정한 공격자가 시도할 수 있는 경로.

## 🟠 빨리 손봐야 할 9가지

### 통계가 어긋나는 문제 4가지

**A. 사장님이 사용하는 상담 화면에서 시술 끝내도 손님 방문 횟수가 안 늘어요**

`/consultation` 플로우 (다국어 상담 화면)로 시술을 끝내면, 그 손님의 **방문 횟수와 누적 매출이 0에서 안 움직여요.**
"즉시 매출"이나 "현장 시술"로 끝낼 땐 정상으로 올라가는데 이 경로만 빠져있어요.
→ 외국인 손님이 많은 샵에서 통계가 자꾸 0건으로 나옴.

**B. 업셀링 매출이 2배로 표시될 수 있어요**

대시보드의 "업셀링 리포트"가 한 매출 건에 들어간 옵션 값을 **두 번 계산**할 가능성이 있어요. 예를 들어 스톤 추가 1만 원이 들어간 시술이 업셀링 2만 원으로 잡힘.

**C. 사전상담을 밤늦게 제출하면 다음 달로 넘어갈 수 있어요**

손님이 5월 31일 밤 11시 50분에 사전상담을 제출하면, **6월 1일 사전상담으로 집계**돼서 5월 통계에서 사라져요.

**D. "인기 디자인" 차트에서 자석네일이 "원컬러"로 잡혀요**

대시보드 한쪽에선 "자석"으로 정확히 잡는데, 다른 차트에선 자석을 원컬러로 변환해서 보여줘요. → 같은 데이터인데 화면마다 다른 숫자.

### 예약/슬롯 문제 2가지

**E. 사전상담 링크 시간 슬롯에서 지난 시간이 예약 가능으로 보일 수 있어요**

서버가 한국 시간이 아닌 UTC로 "지금 몇 시"를 계산해서, 오전 9시 전에는 **이미 지나간 슬롯도 예약 가능으로 떠요.**

**F. 두 손님이 동시에 같은 슬롯을 예약할 수 있어요**

사전상담 슬롯에서 "예약됨" 체크가 화면에서만 이뤄지고 DB에선 막지 않아서, **0.1초 차이로 들어온 두 손님이 같은 시간에 동시 예약**되는 사고가 가능해요.
→ 사장님이 같은 시간에 두 손님을 받는 상황.

### 보안 3가지

**G. 사전상담 참고 사진 업로드 폴더가 다른 샵 폴더로 들어갈 수 있어요**

손님이 사전상담에서 올리는 참고 사진의 저장 폴더 권한이 명확하지 않아요. 직접 URL 조작하면 **다른 샵 폴더에 사진을 올릴 가능성**이 있음.

**H. 사전상담 데이터의 접근 권한이 명시되어 있지 않아요**

손님 이름·전화번호가 들어있는 사전상담 테이블에 권한 정책이 없어서, **누구나 모든 샵의 사전상담 내용을 볼 수 있을 가능성**이 있어요. (Dashboard에서 별도 설정 안 했다면)
→ Supabase 대시보드에서 직접 확인해야 함.

**I. 손님이 임의 샵에 가짜 예약 폭탄을 보낼 수 있어요**

URL의 샵 ID만 알면 익명으로 예약 요청을 무한정 만들 수 있어요. 사장님 알림이 가짜 예약으로 도배될 수 있음.

## 🟡 시간 날 때 손봐도 되는 19가지

### 회원권 자잘한 버그

- 다 쓴 회원권이 가끔 "1회 남음"으로 잘못 표시
- 횟수가 0인데 수동 차감 호출하면 1회만 깎이고 호출자한테 알림 없음
- 데모 데이터에 진짜 손님과 이름이 같으면 진짜 손님이 덮어 써짐 (shop-demo 에서만)

### 통계 자잘한 오차

- 재방문율: 같은 손님이 2번 오면 양쪽 다 2배로 잡힘
- 매출 등록 시 시간을 안 적으면 무조건 정오로 기록 → 시간대 차트에 12시 매출이 부풀려짐
- 인기 디자인 KPI와 서비스 분류 차트의 계산 기준이 달라서 숫자가 안 맞음
- "골든타임" 계산이 시스템 시간대를 따라서 ±1일 어긋날 수 있음
- 전월 데이터가 없을 때 0%로 표시 → "데이터 없음"으로 바꾸는 게 좋음

### 사전상담 링크

- 링크 유효기간이 지나도 슬롯 목록이 보일 수 있음 (만료 처리 누락)

### 보안 5가지

- 공유 카드에서 사장님 전화번호·주소가 같이 노출됨
- 사전상담 사진 폴더가 "전체 공개"로 설정됐을 가능성 (Dashboard 직접 확인 필요)
- 동일 IP에서 무한정 예약 요청 가능 (브라우저 새로고침으로 우회됨)
- 손님 이름·전화번호에 글자 수 제한이 DB 단에서 없음 → 5만 자 이름 등록 가능
- 테마 부트스트랩 스크립트가 인라인 방식이라 향후 확장 시 보안 약점 가능성

### 화면 일관성 8가지

- 가격 표기가 "₩50,000"과 "50,000원"이 한 화면에 섞여 나옴
- 사장님 상담 플로우 문서에 단계 순서가 잘못 적혀있음 (코드와 불일치)
- 홈 화면 CTA 일부 글자가 다국어 전환 안 되고 한국어 고정
- 사전상담 상담 페이지 헤더가 외국어 + 한국어 보조 표시 안 됨 (하위는 정상)
- "데이터 없음" 안내 디자인이 화면마다 제각각 (공용 컴포넌트 있는데 안 씀)
- 날짜 형식이 "2026.05.29"와 "5월 29일 금요일"이 혼용
- 모달과 바텀시트 기준이 화면마다 달라서 일관성 부족
- 일부 버튼 터치 영역이 모바일 권장(44px)보다 작음

## 전체 흐름 한 페이지로 이해하기

### 사장님이 BDX를 처음 쓸 때

```
회원가입(이메일 또는 구글) → 7단계 온보딩 → 홈 화면

홈 화면에서 할 수 있는 것:
├─ 오늘 예약 보기
├─ 새 예약 등록
├─ 즉시 매출 등록 (간단한 매출)
├─ 현장 시술 시작 (포트폴리오에서 디자인 골라서)
└─ 사전상담 링크 복사 → 손님에게 공유
```

### 손님이 사전상담 받는 흐름

```
사장님이 링크 공유
→ 손님이 모바일로 접속 (4개 언어 지원)
→ 디자인 고르기 → 네일 상태 → 정보 입력 → 제출
→ 사장님 홈 화면에 "응답 완료" 배지
→ 사장님이 "이 정보로 시술 시작" 누르면 바로 현장 모드로 진입
```

### 현장에서 시술하는 흐름

```
디자인 선택 → 옵션 선택 → 시술 시작 (타이머)
→ 시술 중 추가 옵션 (스톤·파츠 등)
→ 정산 (현금/카드/회원권/복합)
→ 완료 (사진 촬영 → 공유 카드 → 홈)
```

### 회원권이 어떻게 빠져나가는지

```
회원권 등록 (100만 원짜리)
→ 손님 시술 결제 시 "회원권" 선택
→ 시술비만큼 자동 차감 (예: 5만 원 → 잔액 95만 원)
→ 잔액 부족하면 차액만 현금/카드로 받기
→ 매출 통계엔 차감된 5만 원 + 차액 모두 합산
```

## 확인 필요 (Supabase Dashboard)

다음은 코드만 봐서는 알 수 없어요. Dashboard에서 직접 확인 필요:

- `consultation_records` RLS의 anon SELECT 정책이 `share_card_id IS NOT NULL` 한정인지
- `get_booking_for_pre_consult` RPC 내부에서 shopId 검증하는지
- `pre_consultations` 테이블 RLS 활성화 여부 (`SELECT relrowsecurity FROM pg_class WHERE relname='pre_consultations'`)
- `pre-consult-refs` Storage 버킷이 `public=false`인지 + 폴더 권한 정책
